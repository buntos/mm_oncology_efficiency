## 1. Ошибки v1.0.0 и их причины

Воспроизведены на неизменённой v1.0.0: `results/stage31_v1_0_0_archive/reproduce_v1_0_0_resource_bugs.py` → `reproduce_v1_0_0_resource_bugs.json`.

1. **Потеря времени и пиков памяти обучения после resume.** Ресурсы копились в `state["epoch_res"]`, а `_record_phase("train", …)` вызывался после последнего checkpoint обучения (`phase="trained"`). Промежуточные checkpoint внутри обучения тоже сохранялись до учёта текущего участка.
   - Воспроизведение: в памяти train wall 0.090 с, в checkpoint 0.0, после resume итоговая строка эпохи 1: train wall 0 и peak RSS 0.
   - Checkpoint после 2 попыток также содержал train wall 0.
   - Веса совпадали с непрерывным прогоном.
2. **Стоимость checkpoint учитывалась после сериализации.** `_save()` добавлял время и `checkpoint_count` уже после записи. Стоимость фиксирующего сохранения переносилась в строку `resources` тоже после записи. Воспроизведение: в памяти `checkpoint_count=4`, в checkpoint `3`, время I/O в checkpoint меньше. Повторное открытие пересобрало бы таблицу с уменьшенными значениями.

Общая причина: фактические затраты хранились в том же объекте, что и логическое состояние, а сохранялись в момент, когда текущий замер ещё не был завершён.

## 2. Исправление

**Логический прогресс и фактическая работа разделены.**
- **Логическое состояние** — только в checkpoint: модель, optimizer, scaler, RNG, эпоха, фаза, следующая группа, счётчики попыток, метрики, группы, прогнозы, выбор модели. Ресурсных полей в нём больше нет.
- **Фактическая работа** — в `resource_journal.jsonl`:
  - журнал только дописывается, каждая строка сразу сбрасывается на диск (`flush` + `fsync`) и никогда не переписывается;
  - событие пишется сразу после завершения измеряемого блока: подготовка, **каждая** попытка обновления, validation, диагностика, **каждая** запись checkpoint, вспомогательный I/O;
  - у события есть `session_id`, порядковый номер, тег эпохи, фаза или группа, номер checkpoint, wall и CPU time, пики CUDA allocated/reserved и sampled peak RSS блока.
- **Все ресурсные таблицы — чистая функция журнала.** Они каждый раз пересобираются целиком; накопления в состоянии нет, поэтому двойной учёт и уменьшение уже записанных значений невозможны.
- **Стоимость checkpoint** — отдельное событие `checkpoint_io` с номером checkpoint, записанное после того, как checkpoint стал устойчивым. Дополнительный checkpoint «ради времени предыдущего» не нужен.
- **Повтор после отката:** логические шаги считаются один раз (`train_attempts_logical`), фактическая работа — вся (`train_attempts_executed_work`); разница — `train_attempts_replayed`. Повторные validation и диагностика видны через `*_blocks` и `*_replayed`.

**Обработка сбоев журнала:**

| Ситуация | Обработка |
|---|---|
| Оборванная последняя строка | При следующем открытии дописывается перевод строки (`repaired_truncated_tail`); при чтении нечитаемые строки пропускаются и считаются (`journal_unparsable_lines`), итог помечается нижней границей |
| Checkpoint записан, событие о его записи — нет | При старте каждый checkpoint на диске без события `checkpoint_io` записывается один раз как `checkpoint_io_unmeasured`: эпоха берётся из самого checkpoint, стоимость не подставляется. В строке эпохи: `checkpoints_unmeasured`, `checkpoint_io_wall_is_lower_bound=True` |
| Событие сохранено, но модель откатилась к более раннему checkpoint | Событие остаётся как фактическая работа; повторное выполнение даёт `*_replayed`; логические таблицы (из checkpoint) не дублируются |
| Повторная сборка таблиц | Пересборка из журнала с дедупликацией по (`session_id`, `seq`); значения не суммируются повторно |
| Повторное открытие завершённого прогона | Новая сессия пишет только события без тега эпохи (подготовка, загрузка, проверка `best_model`, сборка таблиц), поэтому исторические строки `resources_by_epoch.csv` не меняются; сессия видна отдельно в `resource_sessions.csv` (`post_completion_session=True`) и `active_seconds_post_completion_sessions` |
| Блокировка CSV (Excel) | Предупреждение; таблица пересобирается из журнала при следующей записи |

Ограничения не изменены: архитектура, веса и инициализация, LR, optimizer, AMP, BN, порядок пациентов, выбор патчей, аугментации, K, seed, разбиения, правило остановки и выбор лучшей модели. Добавлено только поле `_save_tag` (тег эпохи и метка сохранения) в состояние checkpoint — для атрибуции неизмеренных записей; на обучение оно не влияет.

## 3. Границы измерений

Все времена — wall-clock (`perf_counter`) и CPU-время процесса (`process_time`, все потоки) — **не «GPU time»**. Пики памяти считаются по каждому блоку и объединяются максимумом; CUDA peak сбрасывается в начале блока, RSS опрашивается каждые 50 мс.

| Компонент | Что входит |
|---|---|
| `setup` (на сессию) | от старта скрипта до построенной модели: импорт torch и прочее после запуска интерпретатора, проверка бандла Stage 28, хешей, весов и протокола, индекс данных, построение модели |
| `train` (`train_attempt`, на эпоху) | каждая попытка обновления: чтение и проверка хешей PNG, декодирование, аугментация, перенос на GPU, forward/backward, unscale, `optimizer.step` / AMP update, `zero_grad`. **Не входит** запись checkpoint; **пики обучения больше не включают сериализацию checkpoint** (в v1.0.0 включали) |
| `validation` | 186 пациентов × 64 патча: чтение, inference, CE, метрики |
| `diagnostics` | эпоха 0 и после каждой эпохи: 20 train-eval пациентов, изменение весов за эпоху и от инициализации |
| `checkpoint_io` | одна запись checkpoint: преобразование состояния, копирование на CPU, сериализация, fsync, хеш, атомарное переименование, удаление старых поколений |
| `aux_io` | загрузка checkpoint при старте, параметры начала эпохи, экспорт и проверка `best_model`, сборка таблиц (сессионные — без тега эпохи) |
| `active_seconds` (на сессию) | от старта скрипта до последнего события сессии; `other_wall_seconds` — то, что не попало ни в один блок (циклы, запись журнала, вывод). Финальная сборка таблиц после `session_end` не измеряется |
| Итог прогона | `active_seconds_training_sessions` (включая повторную работу) и отдельно `active_seconds_post_completion_sessions` |

## 4. Что известно и неизвестно после аварии

- **Известно точно:**
  - логическое состояние на последнем целом checkpoint;
  - стоимость каждого завершённого блока, включая работу, которая затем была откатана и повторена;
  - число повторённых попыток и прогонов validation/диагностики;
  - какие checkpoint записаны без замера.
- **Неизвестно:** время после последнего события аварийной сессии (незавершённая попытка, validation в процессе, запись checkpoint без события). Такие сессии помечены `clean_end=False`, `active_seconds_is_lower_bound=True`; итог прогона — тоже нижняя граница. Ноль не подставляется, оценки по числу шагов нет.
